 COMMANDS_TAIL.txt — why does a nested (variable-rate) code waste its tail?
 rev 2026-09-30. Everything runs on the server, from the jscc/ directory.
================================================================================

WHAT WE KNOW (ViT, Kodak; tail gain = PSNR at 1/8 minus PSNR at 1/12)

                                   nested code      fixed-rate 1/8 code
  no channel noise (P3b / P1)       -0.02 dB          +1.00 dB
  trained 16-22 dB, at 22 dB        +0.04 (P2)        +0.60 (P3a)
  trained -2..22 dB, at 13 dB       +0.21 (p1)        +1.01 (P3c)

  Nesting, not the channel, empties the tail: even with NO noise the nested
  code's last third carries nothing. In practice the fixed 1/8 specialist
  beats the nested model at 1/8 by +0.29 dB at 1 dB SNR rising to +0.71 dB at
  22 dB (P3c vs p1), while the specialist is useless at small budgets.

THE QUESTION NOW: where does the tail's information die?
  (a) the encoder never puts new information into the tail, or
  (b) it does, but the nested decoder does not read it, or
  (c) neither: the budget sampling simply starves the tail of training signal.
  Each answer calls for a different architecture (bottom of this sheet).

THE PROBES (all noise-free: fast, and noise is not the cause)
  Q2a  freeze P3b's nested ENCODER, train a decoder for 1/8 only    -> (a)/(b)
  Q2b  the same for 1/12 only: the specialisation gain WITHOUT a tail
       tail information the encoder sends = Q2a(1/8) - Q2b(1/12)
  Q1   nested from w1 like P3b, but half of all budgets are the full one
       (--top-prob 0.5): is it just sampling?                        -> (c)
  Q3   (optional) freeze P3b's nested DECODER, train an encoder for 1/8:
       can the nested decoder read an informative tail at all?

--------------------------------------------------------------------------------
 1. THE PROBES (GPU; Q2a/Q2b/Q3 train one half only, 100 epochs; Q1 200 epochs)
--------------------------------------------------------------------------------

FTQ="--trainset DIV2K --validset DIV2K --testset Kodak --img-size 256 \
  --batch-size 16 --amp --training --valid-freq 20 --lr 5e-5 --warmup-steps 200 \
  --channel-type none --snrs 13 --backbone vit"
W1=history/vit_p8d768x10s4_awgn_DIV2K_256_w1/models/last.pt
PR3B=history/vit_p8d768x10s4_none_DIV2K_256_pr3b/models/last.pt
ls -l $W1 $PR3B

# Q2a — nested encoder frozen, decoder for 1/8   -> ..._none_DIV2K_256_fix1-8_frz-enc_q2
CUDA_VISIBLE_DEVICES=0 nohup python main.py $FTQ --pretrained $PR3B --freeze encoder \
  --fixed-cbr 1/8 --max-epoch 100 --tag q2 > q2a_dec_1-8.out 2>&1 &

# Q2b — nested encoder frozen, decoder for 1/12  -> ..._none_DIV2K_256_fix1-12_frz-enc_q2
CUDA_VISIBLE_DEVICES=1 nohup python main.py $FTQ --pretrained $PR3B --freeze encoder \
  --fixed-cbr 1/12 --max-epoch 100 --tag q2 > q2b_dec_1-12.out 2>&1 &

# Q1 — nested, half the budgets full, from w1    -> ..._none_DIV2K_256_top0.5_q1
CUDA_VISIBLE_DEVICES=2 nohup python main.py $FTQ --pretrained $W1 --top-prob 0.5 \
  --max-epoch 200 --tag q1 > q1_top05.out 2>&1 &

# Q3 (optional) — nested decoder frozen, encoder for 1/8  -> ..._fix1-8_frz-dec_q3
CUDA_VISIBLE_DEVICES=3 nohup python main.py $FTQ --pretrained $PR3B --freeze decoder \
  --fixed-cbr 1/8 --max-epoch 100 --tag q3 > q3_enc_1-8.out 2>&1 &

grep -h "froze the" q2*.out q3*.out   # confirms which half is frozen
grep -h "loaded" q*.out               # 0 missing, 0 unexpected

WHAT EACH ANSWER CALLS FOR
  (a) encoder side: a RATE-CAUSAL encoder — tokens attend only to tokens
      earlier in transmission order (or a residual branch fed with the
      prefix's reconstruction), so the tail is computed knowing what has
      already been sent
  (b) decoder side: BUDGET-GATED decoder capacity — extra decoder blocks (or
      experts) that run only when tail tokens are present, so reading the tail
      does not compete with decoding short prefixes
  (c) a sampling recipe; the architecture then has to beat it, not replace it
