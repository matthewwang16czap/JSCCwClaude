 COMMANDS.txt — wave c2: how big is the multi-rate penalty here, and is it in
 the encoder or the decoder?
 rev 2026-10-08. Everything runs on the server, from the jscc/ directory.
 GPUs: ONLY 2, 3, 4 and 5. GPU 0 (kept free) and GPU 1 (broken) are never used.

WHERE WE ARE (docs/NOTES.md, "Cascade wave c1: results"). The depth cascade beat
the grid-trained prefix control by only +0.02 to +0.08 dB on Kodak, and a per-rate
LINEAR stage got all of it: module bodies, spatial context and depth schedules
added nothing. The one knob that moved anything, --cascade-grad, acts on the shared
encoder and only traded the top rate (+0.07 dB at 1/8) against the bottom one
(-0.24 dB at 1/48, vit). So the penalty of serving five rates with one model is
not in the code layout at the bottleneck. This wave asks where it is.

THE QUESTION: under exactly the c1 protocol (fine-tune of the wave-1 checkpoint,
400 epochs, lr 5e-5), how much does a model trained for ONE rate gain over the
multi-rate control, and does that gain need a dedicated encoder, a dedicated
decoder, or both?

  run    model                                trained part        rate    answers
  V1     vit 1/8 specialist                   everything          1/8     the gap at 1/8 (G)
  V2     vit 1/8, encoder frozen at w1        decoder only        1/8     the decoder's share (D)
  V3     vit 1/8, decoder frozen at w1        encoder only        1/8     the encoder's share (E)
  V4     vit 1/48 specialist                  everything          1/48    the gap at 1/48
  W1-W4  the same for swin (W1 1/8, W2 1/48, W3 1/8 decoder only, W4 1/8 encoder only)

All start from the wave-1 checkpoints, like the c1 control, so every run has the
same 400 epochs of extra training; the control is c1's grid run (already done).

  card   queue (in order)                                       about
  GPU 2  V1 vit 1/8 specialist     -> W3 swin 1/8, decoder only    6 h
  GPU 3  V2 vit 1/8, decoder only  -> W4 swin 1/8, encoder only    5.5 h
  GPU 4  V3 vit 1/8, encoder only  -> W1 swin 1/8 specialist       6 h
  GPU 5  V4 vit 1/48 specialist    -> W2 swin 1/48 specialist      6.5 h
  (a full vit job is about 3.8 h, a swin job 2.7 h, from your c1 logs; a run with a
   frozen half is faster. Optional section 4 adds ~4 h on one card.)

GOTCHA: the specialists are evaluated at all five CBRs on purpose: the evaluation
seeds each (SNR, CBR) cell by its position in the CBR list, so only a run scored on
the same five CBRs gets the same channel draws as the c1 control (paired, common
random numbers). Read a specialist at its OWN CBR only; its other rows are
meaningless.
GOTCHA: "froze the encoder" / "froze the decoder" must appear in the frozen runs'
logs (section 2). A frozen half stays in eval mode, so its DC estimates do not move.

# Decision. G = specialist - control at 1/8 (V1 / W1), D = decoder-only (V2 / W3),
# E = encoder-only (V3 / W4), all paired at 1/8:
#   G < ~0.15 dB          the multi-rate penalty is small under this protocol: the
#                         nesting story ends here, and the paper must be about
#                         something else
#   D >= ~0.7 G           the decoder is where rates compete -> next: per-rate low-rank
#                         adapters inside the decoder backbone (no extra compute: the
#                         decoder already runs once per rate)
#   E >= ~0.7 G           the encoder -> per-rate branches of the last encoder blocks
#                         (costly), or report --cascade-grad as a rate-priority knob
#   D + E ~ G, each partial    both halves -> adapters on both sides
#   D + E well below G    the gain needs both halves to adapt together
# And the 1/48 gap: large -> low rates pay too; small -> a top-rate effect only.
