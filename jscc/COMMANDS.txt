WHY WAVE C2 (old sections 2-4) IS RETIRED. It was written on 2026-10-09 for the plan of
that day, before the paper moved to scheduling, and four things are wrong with it now:
  1. Most of it answers questions the paper no longer asks: ViT vs Swin at matched compute
     from scratch (M1, M2: 2000 epochs each, days of two cards), the per-image allocation
     oracle (A1, A2; the scheduling runs measured the content part directly: +0.05 dB),
     AdaTok-style LoRA budget heads and a second seed of the cascade (L1, L2, R1, R2).
  2. Its specialists (V1 1/8, V4 1/48, W1, W2) were to be compared with the c1 control,
     a constant-SNR model. Every scheduling result uses the PIECEWISE-trained model
     (snrc4_s1), and constant-SNR decoders do not decode slot-split codes properly (P-A:
     2-4x worse model errors). The gap c2 measures does not price the per-CBR baseline.
  3. It trains two lengths (1/8, 1/48); the schedulers mostly send 2-4 phases (1/24-1/12),
     and 5/48 was nowhere.
  4. The sheet kept asking for its results ("send 4b-4d") while sections 5-8 used GPU 5,
     which section 3 had queued for c2.
Its replacement is 10.1: one specialist per phase length (1/48 ... 1/8), each trained
exactly like snrc4_s1 (from w1, 400 epochs, --snr-chunks 4) plus --fixed-cbr, then
measured like it (tools/mixed_snr.py --design full) and scheduled like it. If c2 jobs are
still running, 10.0 stops them. If some finished, nothing is lost: see 10.6 (optional).
The old sections 2-4 are in git (commit e322808) if you ever want them.

#       the best causal policy for this model: say so (and a small RL check is a footnote,
#       not the method). >= ~0.3 dB or >= ~5 points somewhere (noisy CQI, slow fading, lost
#       slots, tight frames are the likely places) -> build an RL scheduler for those settings,
#       trained on this model, with our rules as its baselines. optimum - base is what even
#       perfect foresight adds (no causal policy reaches it); "bound - optimum" near 0

# Under a scheduler a code's phases never see "the channel": each goes out in the slot the
# scheduler picked for it, so the SNR every phase sees and the number of phases every user gets
# are MADE by the scheduler. Ours puts the first, most sensitive phases into fading peaks; snrc4
# was trained on i.i.d. chunk SNRs uniform over [-2, 22] dB -- another channel. The test: four
# fine-tunes of snrc4, 400 epochs each, the same recipe; only the channel they train on differs:
#   hf     --snr-chunks 4, the recipe so far (= section 13's HF): the same-budget CONTROL
#   blind  the lengths slope_adv gives, each phase in a slot taken blindly (the user's mean SNR
#          plus a fresh fade): the physical channel at the scheduler's lengths
#   sa     what slope_adv delivers (the mean-PSNR scheduler)
#   sat    what replan_adv delivers at 30 dB (the QoS scheduler)
# sa - blind is what the scheduler's slot SELECTION is worth to the code (the claim); blind - hf
# what the scheduler's lengths and the users' mean SNRs are worth. Each card trains (~4 h), then
#   (1) decodes the ORIGINAL system's schedules (snrc4's utility; the same users, images and slot
#       SNRs for every code): the code's best response, nothing else changes;
#   (2) measures the code per phase (~10 min), fits its utility and lets the scheduler re-plan for
#       it, then decodes those schedules: the full system, the loop closed once.
# GPU 2 first decodes the original system (snrc4, ~20 min). Decodes take ~20 min per code.
# Optional, CPU only: section 13's CPU blocks (13.3, 13.3d-f, 13.4, with 13.0's variables) do not
